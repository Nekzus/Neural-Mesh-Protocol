The SDK ships with a token economy module designed to estimate cost and expose telemetry for MCP operations.

## Estimators

The SDK includes a built-in, zero-runtime-dependency **`o200k_base`** Byte-Pair Encoding (BPE) tokenizer — the industry standard encoding scheme for modern OpenAI models (GPT-4o, o1, o3-mini) and an accurate baseline across major LLM providers (Anthropic Claude 3.5/3.7, Google Gemini 2.0).

Through build-time inlining and AST tree-shaking via `tsup`, the `o200k_base` vocabulary is bundled directly into the compiled distribution. This eliminates **25.95 MB** of external legacy tokenizer dependencies, reducing the installed `node_modules` footprint from **100.95 MB** to **84.43 MB** (-17.1% net reduction).

Both `createTokenEstimator()` (async factory) and `createSyncTokenEstimator()` (synchronous factory) provide immediate, synchronous access to `RealTokenEstimator` out-of-the-box:

```typescript
import {
  createTokenEstimator,
  createSyncTokenEstimator,
  RealTokenEstimator,
  HeuristicTokenEstimator
} from "@nekzus/liop";

// Instantly returns RealTokenEstimator ("o200k_base") synchronously
const syncEstimator = createSyncTokenEstimator();
console.log(syncEstimator.name); // "o200k_base"

// Exact BPE token counting with zero external runtime network or fs calls
const count = syncEstimator.countTokens("Hello world! Logic-Injection-on-Origin");
console.log(count); // 12

// Async factory for full API compatibility
const asyncEstimator = await createTokenEstimator();
```

<Note>
  `HeuristicTokenEstimator` (calculating `Math.ceil(chars / 4)`) remains available as a lightweight algorithmic fallback class if explicit heuristic modeling is desired.
</Note>

## TokenTelemetryEngine

`TokenTelemetryEngine` is a singleton collector for operation-level metrics:

- Input/output token estimates
- Operation type (`tools_list`, `tool_call`, `resource_read`, etc.)
- Duration metadata
- Session-level aggregates

```typescript
import { TokenTelemetryEngine } from "@nekzus/liop";

const telemetry = TokenTelemetryEngine.getInstance();
telemetry.record({
  type: "tool_call",
  method: "tools/call",
  estimatedInputTokens: 120,
  estimatedOutputTokens: 64
});
```

## LiopOTelBridge

`LiopOTelBridge` maps token telemetry into **OpenTelemetry `gen_ai.*` semantics** so external observability backends can ingest LIOP token data seamlessly.

The bridge automatically binds to your global `MeterProvider` and emits the following metrics:
- `gen_ai.client.token.usage` (Histogram)
- `gen_ai.client.operation.duration` (Histogram)

Use this module when you need production cost visibility across local and mesh-routed MCP workloads.

## LiopMeshStatus Integration

The LIOP Agent exposes a local diagnostic tool called **`LiopMeshStatus`** that consumes the `TokenTelemetryEngine` internally to produce a rich, human-readable status block via `formatStatusBlock()`. When an LLM calls this tool, it receives a structured report containing:

- **Session ID** and uptime
- **Estimator model** (`o200k_base` or heuristic)
- **Operation breakdown** — each MCP method called, with input/output token estimates
- **Cumulative totals** — total tokens consumed across the session
- **Cost projection** — estimated cost based on configurable per-token pricing

<Tip>
  The token economy telemetry is **intentionally visible** in the `LiopMeshStatus` output. This transparency enables B2B clients to audit consumption patterns and allows AI agents to autonomously manage their context window budgets without requiring external monitoring infrastructure.
</Tip>

## Deterministic AST Fuel Metering

In addition to token estimation, the SDK provides deterministic computational fuel measurement via `calculateAstInstructionFuel`:

```typescript
import { calculateAstInstructionFuel } from "@nekzus/liop";

const javascriptCode = `
  const total = env.records.reduce((acc, r) => acc + r.amount, 0);
  return { count: env.records.length, average: total / env.records.length };
`;

// Parses Acorn AST, evaluates instruction weight, and quantizes to 100-unit buckets
const fuel = calculateAstInstructionFuel(javascriptCode);
console.log(fuel); // 500 units
```

### Side-Channel Timing Invariance (NIST SP 800-53)

To ensure zero timing leakage across varying private inputs, `calculateAstInstructionFuel` enforces 100-unit bucket quantization:

$$\text{Fuel} = \lceil \frac{\text{RawASTScore}}{100} \rceil \times 100$$

Across extensive automated profiling (50 consecutive executions on synthetic transaction batches), payloads with identical AST topology evaluating divergent secret inputs yield a standard deviation of strictly zero (`stddev = 0`).

## Context & Token Economy vs Traditional MCP (Context-Pulling)

Traditional MCP requires pulling entire raw datasets across the network into the LLM context window before filtering or analysis can occur. LIOP executes sandboxed logic directly on the origin node, returning only aggregated proofs.

### Empirical Efficiency Comparison

| Metric | Traditional MCP (Context-Pulling) | LIOP (Logic-on-Origin) | Net Savings |
|:---|:---|:---|:---|
| **Paradigm** | Raw Data Extraction to Agent | Sandboxed WASI Execution in Origin | **Zero Data Egress** |
| **Input Context Tokens** | ~16,000 – 48,000 tokens | ~320 – 650 tokens | **98.9% – 99.3% reduction** |
| **Output Context Tokens** | ~1,200 – 4,500 tokens | ~80 – 180 tokens | **93.3% – 96.0% reduction** |
| **Network Wire Transfer** | ~195 KB (raw JSON payload) | ~801 B (gRPC envelope + receipt) | **99.6% reduction** |
| **LLM Context Saturation** | High (triggers truncation / sliding window) | Minimal (preserves reasoning capacity) | **Zero Context Bloat** |
| **PII / Exfiltration Risk** | Severe (raw records leave perimeter) | Zero (blocked by 6-layer shield) | **Cryptographically Sealed** |
